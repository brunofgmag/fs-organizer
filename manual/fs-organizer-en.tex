\section{What this program does}

FS Organizer turns Microsoft Flight Simulator addons on and off without moving a
single file.

Your addons live in a folder of your own, outside the simulator, which the
program calls a \ui{library}. Its subfolders become \ui{categories}. Enabling an
addon creates a link inside a folder the simulator reads, which the program
calls a \ui{destination}; disabling removes that link and nothing else. The real
files never leave the library, and that is why swapping tens of gigabytes of
content is instant.

The link is an NTFS directory junction. To the simulator it is the folder; to
you it is an entry FS Organizer creates and removes.

\subsection{What the program does not store}

Whether an addon is enabled \textbf{is never written down anywhere}. On every
scan the program reads the destinations from the disk and answers for what it
found there. That has a practical consequence: moving folders around from the
outside, with Explorer or with another program's installer, never leaves the app
saying one thing while the simulator does another. Read again and it is current.

\subsection{Profile}

A \ui{profile} is one simulator installation with its destinations and its
libraries. Anyone running Flight Simulator 2020 and 2024 on the same machine has
two profiles, and the program only touches what is in use: marking another one
active is what switches the target of everything.

\subsection{Link type}

In \ui{Options}, under \ui{Links}, the program offers two types.

\begin{description}
  \item[Directory junction] Needs no administrator and crosses local volumes. It
    is the default, and the only path that has been tested.
  \item[Symbolic link] Only for a library on a network path, where the junction
    does not reach. It needs a Windows privilege; without it the program
    explains the refusal instead of failing quietly.
\end{description}

Switching the type changes new links only. The ones that already exist stay as
they are.

\section{Presets}

Presets come first in this manual because they are the part nobody gets right
by trial. A preset looks like a list of addons, but it is a list of addons
\textbf{plus an apply mode}, and the same preset gives three different results
depending on the mode.

\subsection{What a preset holds}

A preset saves a set of enabled addons under a name. Enable what you want to
fly with and use \ui{New from enabled addons}.

The \ui{Content} column says how many addons it names and how many categories
they are in. The \ui{Updated} column says when it was last saved.

A preset can also control the simulator's startup entries, covered in
section~\ref{sec:presets-startup}.

\subsection{An applied preset}

The \ui{If applied} column says how many addons would change state if you
applied that preset now. When the number is zero, the table says
\ui{Already applied}.

\textbf{This is always measured as Replace}, even if you mean to apply the
preset another way. A preset naming three addons, all enabled, shows as applied
only if \textbf{nothing else} is enabled. If a fourth addon the preset does not
name is enabled, the preset is not applied, because Replace would disable that
fourth addon.

This is deliberate: the column answers ``is my installation the way this
preset describes it?'', and only Replace reads a preset as a description of the
whole installation.

\subsection{The three apply modes}

\ui{Apply as} chooses between three readings of the same preset.

\begin{description}
  \item[Replace] Enables the preset's addons and disables everything else.
  \item[Accumulate] Enables the preset's addons and leaves the rest as it is.
  \item[Disable] Disables the preset's addons. Addons the preset lists as
    disabled are ignored.
\end{description}

Before you apply, the \ui{Plan} panel shows what will happen, in five groups
that add up to the whole count:

\begin{itemize}
  \item \ui{To enable}: addons in the preset that are disabled now.
  \item \ui{To disable}: addons going off, either because the preset says so or
    because Replace leaves them out.
  \item \ui{Already as the preset asks}: nothing happens to them.
  \item \ui{Not found in the library}: addons the preset names that are no
    longer in the library. The program lists them and applies the rest.
  \item \ui{Requested, but not applied}: startup entries the preset asks for
    that could not be changed.
\end{itemize}

\shot{03b-presets-plan.png}{The plan of the ``Voo curto'' preset, read as
Replace. The five groups add up to the whole count, and the sentence under them
says the 4 not in the preset are among the 4 being disabled.}

\subsection{What Replace disables by omission}

Applying as Replace disables the addons that are enabled now and that the
preset does not name. They show up under \ui{Disabled by Replace}, and
\ui{Show them} opens the list.

\textbf{They are already included in the plan's count.} If the plan says
``disables 12'' and the list has 5 names, the total is still 12: 5 left out of
the preset and 7 the preset asks to disable.

\subsection{The return preset}

Before applying any preset, the program \textbf{saves what is enabled at that
moment} as the profile's return preset. \ui{Back to the previous set} applies
it.

If it cannot be saved, because the presets folder is full or read-only,
\textbf{nothing is applied}, so there is always a way back.

The return is not the same as \ui{Undo last change}:

\begin{description}
  \item[Undo last change] Undoes exactly what you just applied. An import or a
    quarantine operation done afterwards uses up the undo.
  \item[Back to the previous set] Applies the return preset, which is a preset
    like any other. It survives imports and quarantine operations, because it
    does not depend on the journal.
\end{description}

Applying a preset is a single batch: \ui{Undo last change} takes all of it
back at once.

\subsection{Presets and startup entries}
\label{sec:presets-startup}

On the preset's \ui{Startup} tab, a checkbox makes the preset also control the
programs the simulator launches with itself. Checking it saves the entries
enabled at that moment, and you can then enable or disable each one there.

If startup management is off in \ui{Options}, the preset's entries \textbf{are
not applied}, and the program says how many. The rest of the preset is applied
normally.

If an entry the preset names is no longer in the simulator's file, it is listed
instead of recreated. The program never adds a startup entry.

\section{First setup}

On the first run the program looks for the simulator installations on the
machine and asks for two things.

\begin{description}
  \item[The simulator] Choose the installation this profile will manage, from
    the list it found, or point at a folder by hand. If the folder you point at
    does not look like a simulator destination, which is usually called
    \where|Community|, the program says so and uses it anyway.
  \item[The library] Choose the root folder where your addons are kept, outside
    the simulator. Its subfolders become categories.
\end{description}

When you register a very deep library, the program shows how many characters
that root consumes and how many are left for the addon, next to a short root for
comparison. Nothing is blocked: addons that go past the Windows limit say so
when it matters, and \ui{Diagnostics} keeps the longest path of each library.

Anyone coming from MSFS Addons Linker can bring its configuration over in
\ui{Options}, through \ui{Import from MSFS Addons Linker}. Nothing is moved or
deleted: importing registers the library, the categories and the presets that
are not here yet.

\section{Library}

The \ui{Library} tab is the tree of your addons, grouped by the categories that
are the subfolders of the root. The checkbox on each row turns it on and off.

\shot{01-library.png}{The library, with the categories open and the panel of the
selected addon on the right.}

\subsection{The columns}

\begin{description}
  \item[Addon] The folder name.
  \item[Version] What the addon's \where|manifest.json| declares.
  \item[Enabled] Whether a link to it exists in a destination right now.
  \item[Destination] Which destination it is linked in, and whether that
    destination is pinned.
  \item[Link] Whether the link finds the folder. When it does not, the link is
    broken.
\end{description}

Three marks appear on a row when something is out of place: \ui{Broken link},
\ui{In conflict} and \ui{Two copies}. Each one has a section in this manual.

\subsection{Enabling and disabling in bulk}

Selecting several rows and using \ui{Enable selected} or \ui{Disable selected}
does it all in one batch. Past a certain number, the program asks
first.

If an addon's spot is taken by another addon of yours, the program does not
refuse: it offers the \textbf{swap}, which goes out and comes in as one
operation, with one line in the journal and one undo.

\subsection{Categories}

The tree's context menu creates, renames and deletes categories, and moves
addons between them. Only an empty category can be deleted.

\ui{Suggest categories} reads rules about the folder name and about the
\where|manifest.json| and proposes moving whatever is out of place. The rules
that are reliable come checked; the livery rule is often wrong, so it comes
unchecked: review it before applying.

A folder counts as a category while it groups addons, and the program writes a
hidden \where|.fsorg-category| inside the ones it knows about so that a category
which loses its last addon keeps being one. It marks them when it registers the
library, and \ui{Categories} in the options marks them again later.

A folder that groups no addon and carries no \where|manifest.json| of its own is
treated as an addon, so it can be enabled, moved and deleted like any other. That
is what a converted package the simulator writes beside yours looks like, and
what a scenery object library that ships without a manifest looks like too.

\subsection{Pinning the destination}

By default an addon is linked in the profile's default destination. \ui{Always
use}, followed by a destination, ties an addon or a whole category to it. When a pinning
names a folder that has stopped being a destination of the profile, the program
says so and uses the default destination while that is true, without deleting
the pinning from the configuration.

\subsection{Repointing}

When a link exists but points at the wrong place, or at a folder that is gone,
\ui{Repoint to the library} fixes it. Repairing never touches the real files:
only the reparse node is rewritten.

\section{Destinations}

The \ui{Destinations} tab shows everything inside the folders the simulator
reads, including what is not yours. Each entry gets a classification.

\shot{02-community.png}{The destinations, with the classification filter at the top
and the count of each kind in the footer.}

\begin{description}
  \item[Managed] The simulator loads it from your library. This is the normal
    state.
  \item[External] A regular folder another program installed, not in a library
    yet.
  \item[Divergent] The other program put its own copy back, so there are two
    copies.
  \item[Vanished] The library copy is gone, removed by the other program. There
    is nothing to repair: the files no longer exist on this computer.
  \item[Broken] The link points to a folder that does not exist.
  \item[Unavailable] The drive is not connected right now. It can come back, so
    the program offers no cleanup.
  \item[Unmanaged] A regular folder, not in a library yet.
  \item[Duplicated] Linked in more than one destination.
  \item[Substituted] Something wrote a regular folder over a link this program
    made. The simulator loads that folder and ignores the library copy.
\end{description}

The filter at the top narrows the list by classification, and \ui{Select all
shown} selects exactly what is visible.

\subsection{Taking over another program's folder}

\ui{Import this folder} moves the folder into your library and leaves a link in
its place. From then on it is an addon of yours like any other.

The risk is that \textbf{the other program will not know about the link}. Its
next update may write into the link, or replace it with a regular folder and
leave you with two copies. When that happens, the entry shows up as
\ui{Divergent} and the program asks which copy to keep.

You can give the addon back to the program that installed it later, through
\ui{Delete from the library}.

\section{Importing}

Importing copies a regular folder into the library and leaves a link in its
place. The original is removed only after the copy is verified.

The operation has five steps, and the journal records each one:

\shot{27-community-import.png}{The import dialog, which says how much is about to
be copied, into which library and category, and where the addon will end up.}

\begin{enumerate}
  \item Copy to a temporary folder.
  \item Check the copy.
  \item Put the copy in place.
  \item Remove the source folder.
  \item Create the link in the destination.
\end{enumerate}

While the copy runs, a window shows which folder it is on, how far it has got
and a \ui{Cancel} button. Cancelling deletes nothing: what was already copied
stays where it is, for the resume.

\subsection{Check after copying}

In \ui{Options}, under \ui{Links}, the check comes in two forms.

\begin{description}
  \item[By structure] Checks the count and the size of every file. It is the
    default.
  \item[By hash] Reads both sides in full and compares the bytes, which catches
    a change the size hides. It makes an import several times slower, and the
    number of files weighs more than their size.
\end{description}

If the copy does not match, nothing is removed.

\subsection{Half finished imports}

If an import is interrupted, the next run offers three ways out: resume, discard
the half finished copy, or leave it as it is. The original files are still where
they were, and nothing was removed from the destination.

When the half that stopped is a conflict resolution, only discarding is offered,
because both copies are still where they were.

\section{Quarantine}

When you resolve a conflict between two copies of an addon, the copy you do not
keep goes to the quarantine instead of being deleted. \textbf{Nothing leaves the
quarantine unless you ask}, and nothing is deleted on the way in.

Next to each item the program records where it came from. That record does not
depend on the journal, so an item can be restored even if the journal is gone.
The table shows both sources, \ui{The record says} and \ui{The Journal says},
and flags when they disagree.

\shot{05-quarantine.png}{The quarantine, with the origin of each item and the flag
for when the record and the journal disagree.}

\ui{Restore} sends each folder back to where it came from. Nothing is
overwritten: conflicts are listed with both versions, and replacing moves what
is there to the quarantine. \ui{Discard} deletes permanently, and asks first.

\section{Deleting an addon from the library}

\ui{Delete} offers three routes, and says up front when one of them will not
work.

\begin{description}
  \item[Move to the Recycle Bin] You can restore it from the Recycle Bin. The
    program refuses this route when the selection does not fit in the Recycle Bin
    of that volume, or when the addon holds a path past the 260 characters the
    Recycle Bin stops at. Windows may remove older items from the Bin to make
    room.
  \item[Delete permanently] This cannot be undone.
  \item[Give it back to the program that installed it] Only offered for an
    addon that came from another program. The files move back to the folder
    that program keeps them in, and leave the library.
\end{description}

Turning the addon off is part of the deletion and happens because you asked for
it: the link goes with the addon.

\section{Simulator}

The \ui{Simulator} tab has two panels, and both change files that belong to the
simulator. For both, the program keeps a backup of the file next to it, and
neither changes anything while the simulator is running.

\subsection{Startup entries}

The simulator has a file (\where|EXE.xml|) that lists the programs it launches
with itself. The \ui{Startup entries} panel shows them and lets you enable or
disable each one without editing XML.

The program \textbf{only enables or disables entries that already exist}. It
never adds, removes or reorders them.

\shot{19-simulator-startup.png}{The startup entries, with the program each one
launches and its switch.}

This panel starts off, and while it is off the program neither reads nor writes
that file.

When you disable an addon that has a startup entry, the program warns first:
if the entry stayed enabled, the simulator would keep trying to launch a program
that is no longer there. Disabling both is a single operation, with one line in
the journal and one undo.

\subsection{Package list}

The simulator ships its own airports. When one of your airports covers the same
place as one of them, the \ui{Package list} panel shows the pair and lets you
disable the simulator's airport.

Disabling it changes \textbf{one value} in the package list. Nothing is added,
removed or reordered, and an entry without that value is left alone rather than
edited, because invalid XML makes the simulator reset the whole list.

For two addons \textbf{of your own}, the program only shows the pair: to choose
one, disable the other on the \ui{Library} tab.

This panel also starts off, and while it is off the file is neither read nor
written.

\section{Documents}

The \ui{Documents} tab finds the PDFs your addons include and opens them inside
the program. \ui{Scan the library} looks for PDFs in every addon, and the result
is saved, so later scans are quick.

What it finds is split in two: \ui{Documents} and \ui{Charts}. One addon can
include one manual and a hundred and fifty charts, which is why the count comes
before the list. Charts are grouped by airport, and by type when the addon ships
a catalogue describing them.

The reader has an outline, search, fit to width and bookmarks. A bookmark you do
not name takes the page number. \ui{Open in a separate window} moves the reader
out of the tab.

\shot{26-documents.png}{The documents tab: charts grouped by airport on the left,
the reader in the middle and the outline of the document on the right.}

Charts and documents start with different settings: on a chart the mouse wheel
zooms and dragging moves the page; on a document both start off. The two
toggles on the toolbar say what they do.

\section{Diagnostics}

The \ui{Diagnostics} tab reports what the scan found. Every number shows when it
was measured, and you can measure again at any time.

\shot{09-diagnostics-size.png}{The size on disk section, with the total per category
and per addon, and the time of the measurement.}

\begin{description}
  \item[Destination entries] How many entries there are of each kind, and the
    longest path in each library.
  \item[Broken or unavailable] What is broken and what is on a disconnected
    drive, with a button to repair the broken links.
  \item[Quarantine] How much space the quarantine takes. Nothing is emptied from
    here.
  \item[Size on disk] How much each category and each addon takes. It may take a
    few seconds; \ui{Stop} stops after the addon being measured.
  \item[Airports in the scenery] Scans the scenery of every addon and sorts it
    into addons with an airport code, with an unreadable airport record, with
    navigation data instead of scenery, and without an airport record.
  \item[Modules loaded] Reads the report the simulator writes after a slow load.
    The simulator does not report loading time per package, so this shows which
    module each package loaded and how much memory it holds.
\end{description}

\subsection{Finding the culprit}

When the simulator crashes and you do not know which addon causes it,
\ui{Find the culprit} searches by halves. It disables half of your addons, you
launch the simulator and answer \ui{It crashed} or \ui{It worked}, and each
round rules out half of the suspects.

Before you start:

\shot{31-diagnostics-bisection.png}{The search for the culprit, with the current
round, what has been ruled out and the two answers the user gives.}

\begin{itemize}
  \item The search works on \textbf{units}: one addon, or a group of addons that
    must stay together because they share a model folder. The panel says why a
    group is together, and offers to split it when that is safe.
  \item The first round disables \textbf{all} your addons, to tell whether the
    cause is among them at all.
  \item Your setup is saved before the first round and restored when the search
    ends, however it ends. If the program is closed during the search, it offers
    to restore it the next time it opens.
\end{itemize}

The search assumes a single culprit. If the crash only happens with two addons
enabled together, the result may point to the wrong one, and the panel says so.

\section{Journal}

Every operation that writes to the disk becomes a line in the \ui{Journal}. Lines
are only ever added, nothing on this screen writes to the disk, and \textbf{the
program never deletes it}.

Each line shows when, which operation, which addon, which library, source,
destination and result. \ui{Failures only} narrows the list to what went wrong,
and the search covers addon, path and operation.

\ui{Undo last change}, on the \ui{Library} tab, takes back the whole last
batch, not one operation inside it.

\section{Options}

The gear in the header opens the options, in five tabs.

\shot{10-options-profiles.png}{The profiles and libraries tab of the options.}

\begin{description}
  \item[Profiles and libraries] Adds and removes profiles, changes destinations,
    and adds and removes libraries. Removing a library deletes no files: links
    that pointed at it keep working in the simulator, but FS Organizer stops
    managing them. \ui{Categories} says how many category folders of that
    library are already marked and how many would be, and marks them or removes
    all markers.
  \item[Links] The link type and how imports are verified.
  \item[Updates] Automatic, notify or manual. Automatic downloads new versions
    and installs them when you close the program.
  \item[Language] English and Brazilian Portuguese. The change takes effect
    right away, with no restart.
  \item[About] The version, the licence and the credits.
\end{description}

\section{Where things are kept}

The whole configuration of the program lives under
\where|%LOCALAPPDATA%\fs-organizer|, like this:

\where|settings.json| holds the profiles, the libraries, the destinations and
your choices.

\where|journal\operations.jsonl| is the journal.

\where|presets| holds the presets, one file per preset, plus the return preset of
each profile.

\where|bisection| holds the state of a search for the culprit that is under way.
It stops existing when the search ends.

None of your addon files live there. Deleting that folder deletes the
configuration and the presets, and touches no addon: the program rebuilds what
it knows by reading the destinations and the libraries again.

One thing the program writes outside that folder: the hidden
\where|.fsorg-category| it leaves in the folders of your library that group
addons. It holds nothing, and its whole job is to keep a category counting as one
after it empties. \ui{Categories} in the options takes every one of them back.
